# اجرا، تست، عیب‌یابی و آماده‌سازی انتشار

این راهنما برای فهمیدن روش بررسی پروژه است. نتایج ثبت‌شده در مستندهای قبلی، اجرای تازه روی کد امروز نیستند. برای ساخت این مجموعه راهنما، فایل‌های مستند و ارجاع‌هایشان بررسی شده‌اند و تست‌های برنامه دوباره اجرا نشده‌اند.

**اجرای محلی**

از ریشه پروژه و با Node سازگار با نسخه Next نصب‌شده اجرا کن:

```sh
npm ci
```

روی دستگاه جدید، `predev` پیش از اجرای Next تنظیمات توسعه را آماده می‌کند: `.env.local` خصوصی از نمونه ساخته می‌شود و فقط کلید نشست خالی/ناموجود با یک کلید تصادفی جایگزین می‌شود. کلید معتبر و سایر مقادیر قبلی حفظ می‌شوند. کلید نامعتبر غیرخالی به خطای مشخص ختم می‌شود و خودکار عوض نمی‌شود. این آماده‌سازی نشست یا دادهٔ ساختگی ایجاد نمی‌کند؛ ورود و سبد با همان وردپرس واقعی پردازش می‌شوند.

```sh
npm run dev
```

برای آماده‌سازی مستقل `npm run setup:env` و برای بررسی تنظیمات، دسترسی نوشتن و اتصال واقعی به APIها `npm run doctor` را اجرا کن. doctor فقط مسیرهای احراز هویت و صدور سبد مهمان را می‌خواند؛ پیامک و افزودن کالا انجام نمی‌دهد. `npm run test:environment` نصب تازه، ثبات کلید، نصب هم‌زمان و الزامات production را بررسی می‌کند.

`npm ci` وابستگی‌های lockfile را نصب می‌کند. `dev` سرور توسعه را معمولاً در `http://localhost:3000` بالا می‌آورد. برای بررسی رفتار خروجی production:

```sh
npm run build
npm run start
```

برای پیش‌نمایش محلی خروجی build، `NEXT_PUBLIC_SITE_URL=http://localhost:3000` مجاز است. استثنای HTTP فقط برای فرانت روی `localhost`، `127.0.0.1` یا `[::1]` است؛ کلید معتبر و کوکی Secure همچنان لازم‌اند و ارتباط وردپرس و دامنهٔ عمومی production باید HTTPS باشد. پس از تغییر `NEXT_PUBLIC_SITE_URL` دوباره build بگیر چون مقدار آن در کد مرورگر تثبیت می‌شود.

`start` خروجی قبلی build را اجرا می‌کند. در یک checkout مشترک، build و dev می‌توانند با خروجی `.next` تداخل داشته باشند؛ برنامه انتشار را روی محیط مجزا انجام بده. ساخت build در این نسخه جای اجرای جداگانه lint را نمی‌گیرد.

**تنظیمات را کجا بفهمم؟**

[.env.example](D:/Projects2/nrh_store_nextjs/.env.example) مرجع نام‌ها و مقدارهای نمونه است. `.env.local` تنظیم خصوصی محلی است؛ آن را با مثال جایگزین یا در مستند/لاگ چاپ نکن.

| گروه | متغیرها و اثر |
| --- | --- |
| فرانت و کاتالوگ | `NEXT_PUBLIC_SITE_URL` مبدأ فرانت؛ `WP_API_URL` ریشه REST بک‌اند |
| ورود مشتری | `WP_AUTH_BASE_URL`، namespace، timeout و `AUTH_SESSION_SECRET` |
| دوام نشست | `AUTH_SESSION_MAX_AGE`، `AUTH_SESSION_DATA_DIR` و تنظیم origin در صورت نیاز |
| مدیر بنر | `BANNERS_ADMIN_USERNAME`، `BANNERS_ADMIN_PASSWORD`، `BANNERS_ADMIN_SESSION_SECRET` |
| فایل‌های بنر | `BANNERS_DATA_DIR` |
| سئو و وبهوک | `SITE_INDEXING_ENABLED` و `WP_WEBHOOK_SECRET` |

فقط متغیرهایی که واقعاً عمومی‌اند باید `NEXT_PUBLIC_` داشته باشند. secret نشست مشتری، امضای مدیر بنر و وبهوک مستقل باشند. production برای کوکی Secure به HTTPS نیاز دارد. بعضی مقدارها در build مصرف می‌شوند؛ بعد از تغییر محیط، restart یا build مناسب همان استقرار لازم است.

نبودن کلید نشست اکنون قبل از ارسال OTP یا شروع سبد با کد `configuration_error` و وضعیت ۵۰۳ رد می‌شود؛ جزئیات نام متغیر فقط در ترمینال سرور ثبت می‌شود و مقدار secret چاپ نمی‌شود. راه‌اندازی مستقیم Next نیز در `instrumentation.ts` تنظیمات را بررسی می‌کند. پاسخ ۴۰۱ با کد `session_expired` برای مرورگر مهمان طبیعی است و با خرابی پیکربندی تفاوت دارد. پیام عمومی `unexpected_error` علت مشخصی را ثابت نمی‌کند؛ جزئیات واقعی را در ترمینال سرور بررسی کن.

`prebuild` و `prestart` کلید نمی‌سازند. بررسی زمان build از بررسی اجرای سرور جداست: build محلی به کلید نشست و فضای ذخیره‌سازی production نیاز ندارد و مبدأ HTTP محلی را می‌پذیرد؛ اجرای production همچنان راز ثابت، مبدأ عمومی HTTPS و فضای ذخیره‌سازی معتبر می‌خواهد. مبدأ عمومی انتشار را قبل از build نهایی مشخص کن چون `NEXT_PUBLIC_` در خروجی مرورگر تثبیت می‌شود. `npm run doctor:production` پیش‌نیازهای همین محیط را بررسی می‌کند؛ موفقیت doctor به‌تنهایی تأیید ارسال پیامک، ادغام سبد یا پرداخت نیست. `npm run test:environment` اعتبار JSONهای npm، تطابق lockfile و نبود نشانه‌های merge در فایل‌های پروژه را هم بررسی می‌کند. [گزارش آمادگی production](D:/Projects2/nrh_store_nextjs/docs/production-readiness-fa.md) شواهد واقعی و کارهای باقی‌مانده را جدا توضیح می‌دهد.

**هر نوع تست چه چیزی ثابت می‌کند؟**

| دستور | پوشش و پیش‌نیاز |
| --- | --- |
| `npm run typecheck` | تولید typeهای Route و TypeScript کل برنامه؛ بدون اثبات درستی پاسخ شبکه |
| `npm run typecheck:auth` | بررسی متمرکز احراز هویت با tsconfig همان تست‌ها |
| `npm run lint` | قواعد React، کیفیت کد و مرز import فیچرها |
| `npm run test:headless` | قرارداد کاتالوگ، URL، pagination، schema و وبهوک با fetch جایگزین‌شده |
| `npm run test:auth` | امنیت نشست، ورودی‌ها، nonce، محدودیت تلاش، DAL و ابطال خروج با fixture |
| `npm run test:cart` | عملیات سبد، payload، جداسازی توکن، خطا و آماده‌سازی تسویه با fixture |
| `npm run test:providers:browser` | پاسخ‌های هم‌زمان نشست و چرخه بنر در مرورگر با پاسخ کنترل‌شده |
| `npm run test:auth:browser` | فرم‌ها و محافظت صفحه؛ نشست واقعی گزینه جدا دارد |
| `npm run test:cart:browser` | مسیر خرید روی دسکتاپ/موبایل با سرور محلی و اتصال واقعی سبد |
| `npm run test:cart:live` | چرخه درخواست به ووکامرس واقعی از BFF و نشست مهمان جدا |
| `npm run test:banners` | API محلی، ورود مدیر، آپلود، ذخیره و conflict |
| `npm run test:banners:browser` | پنل واقعی و همگام‌سازی خانه با Playwright |
| `npm run build` | گراف سرور/کلاینت، Routeها و ساخت خروجی production |

تست fixture قرارداد را بررسی می‌کند؛ تحویل واقعی SMS، ایمیل یا پرداخت را اثبات نمی‌کند. تست live به شبکه و تنظیم backend وابسته است؛ شکست خارجی را نباید با پاسخ موفق ساختگی جبران کرد.

**مرورگر و تست‌هایی که داده تغییر می‌دهند**

Playwright در dependencyهای خود این پروژه نیست؛ می‌توان ماژول موجود را با `PLAYWRIGHT_MODULE` برای cart/providerها، `AUTH_PLAYWRIGHT_MODULE` برای auth و `BANNERS_PLAYWRIGHT_MODULE` برای بنر معرفی کرد. بعضی اسکریپت‌ها در این محیط Edge را اجرا می‌کنند. سرور توسعه باید از قبل در حال اجرا باشد؛ URL هر تست متغیر مخصوص خودش را دارد و در ابتدای اسکریپت تعریف شده است.

تست‌های بنر تنظیمات محلی را موقتاً تغییر و در cleanup برمی‌گردانند؛ بدون ویرایش هم‌زمان اجرا شوند. تست live سبد از نشست جدا استفاده و آن را پاک می‌کند. گزینه `AUTH_LIVE_COOKIE_FILE` در تست auth، نشست واقعی داده‌شده را هنگام خروج باطل می‌کند. تست provider، پاسخ‌های مرورگر را شبیه‌سازی می‌کند و حساب واقعی ایجاد نمی‌کند. گزارش‌ها و تصویرهای سبد در `artifacts/cart` هستند؛ نتیجه موفق مرورگر به معنی پرداخت واقعی نیست.

**از کجا عیب‌یابی را شروع کنم؟**

| نشانه | شروع بررسی |
| --- | --- |
| `AbortError` پس از جابه‌جایی | stack، cleanup، Promise catch و guard پاسخ دیررس؛ [راهنمای سبد](D:/Projects2/nrh_store_nextjs/docs/cart-learning-fa.md) |
| خطای `server-only` | زنجیره import از کامپوننت کلاینت به ورودی سروری |
| تصویر خراب | URL، فایل موجود، `remotePatterns` و `sizes` |
| داده قدیمی | به تفکیک Query، کش Next، HTTP/CDN و backend |
| ۴۰۱ | نشست منقضی/نامعتبر یا credential نادرست |
| ۴۰۳ | origin یا مجوز دسترسی |
| ۴۰۹ سبد/بنر | snapshot قدیمی سبد یا revision قدیمی بنر |
| ۴۲۹ | scope محدودیت و `Retry-After` |
| ۵۰۲ BFF | backend، timeout و قرارداد پاسخ؛ خطای backend را با ۴۰۴ محصول یکی نگیر |
| checkout با ۵۰۰ upstream | ناسازگاری ثبت‌شده PHP در `Boom/inc/cart-sync.php` |

برای دیباگ از Network و لاگ محدود استفاده کن؛ رمز، کوکی و OTP را در خروجی نریز. محل `abort()` در stack می‌تواند محل ساخته‌شدن دلیل لغو باشد؛ به‌تنهایی ثابت نمی‌کند خود آن خط خطای منطقی هم‌زمان پرتاب کرده است. خطای مورد انتظار لغو، شکست شبکه و پاسخ واقعی backend را جدا تحلیل کن.

**استقرار این کد به چه زیرساختی نیاز دارد؟**

این برنامه Route Handler، SSR، crypto و filesystem دارد؛ خروجی استاتیک ساده جای همه قابلیت‌هایش را نمی‌گیرد. Next به محیط اجرای سازگار و وردپرس به PHP/دیتابیس خودش نیاز دارد. نمونه `cms.example.com` برای CMS یک پیشنهاد معماری است، نه انتقال انجام‌شده دامنه فعلی.

داده `data/banners` و `data/auth/revoked` باید بین استقرارها حفظ شود. دیسک موقت یا چند نمونه مستقل نیازمند storage و revocation مشترک است. limiter حافظه‌ای هم باید برای چنین میزبانی مشترک شود. reverse proxy باید هدر IP را معتبر بازنویسی کند و مسیر REST، رسانه، nonce و callbackهای لازم را در دسترس نگه دارد.

**پیش از انتشار فروش واقعی**

1. رابط وردپرس نسخه ۱٫۱ نصب و انتقال سبد مهمان، نشست استاندارد حساب و اتصال واقعی درگاه با مالکیت سفارش آزموده شوند؛ پیاده‌سازی محلی و آزمون‌های کنترل‌شده در راهنمای `headless-checkout-sadad-fa.md` ثبت شده‌اند.
2. cart، checkout و session از تمام کش‌های WordPress/CDN خارج شوند.
3. دوام فایل‌ها و ابطال نشست، HTTPS، secretها و محدودسازی مناسب میزبان تأیید شوند.
4. URLهای قبلی، sitemap، schema و اطلاعات کسب‌وکار با سایت زنده تطبیق داده شوند؛ indexing پس از تأیید انتشار فعال شود.
5. backup و راه برگشت، آزمون موبایل، خطا و داده دیررس آماده باشد. هشدار file tracing بنر در سابقه build نیز در بسته‌بندی میزبان بررسی شود.

این فهرست توضیح وابستگی‌های واقعی نسخه فعلی است. پرداخت، DNS یا backend با ساخت مستندات تغییر نکرده‌اند.

**تمرین:** یک خطای عمدی را فقط در fixture تست ایجاد کن و مشخص کن کدام لایه باید آن را بگیرد. سپس برای انتشار فرضی، روی کاغذ محل هر secret، داده پایدار و کش را رسم کن و توضیح بده با restart چه چیزهایی از بین می‌روند.
