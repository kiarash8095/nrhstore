# بررسی نشست و BFF احراز هویت — ۲۰۲۶/۱۰/۳۰

این بررسی با مستندات نصب‌شدهٔ Next.js 16.4.2، مستندات رسمی وردپرس و درخواست‌های واقعی مرورگر انجام شد. تغییرات کد محلی‌اند؛ کامیت، پوش یا استقرار جدید انجام نشده است.

## علت خطای مشاهده‌شده

در مرورگر Production، خطا در `POST /api/auth/send-otp` رخ داد؛ هنوز کدی برای تأیید دریافت نشده بود. وردپرس درخواست فاقد Origin را با HTTP 403 و کد `boom_bad_origin` رد می‌کرد. کد قبلی هر 403 ناشناخته را به `otp_invalid` تبدیل می‌کرد.

برای بررسی قرارداد بدون ارسال پیامک، بدنهٔ خالی به مسیر وردپرس فرستاده شد:

| Origin درخواست سرور | نتیجهٔ وردپرس |
| --- | --- |
| بدون Origin | 403 / `boom_bad_origin` |
| Origin فرانت Vercel | 403 / `boom_bad_origin` |
| Origin پیکربندی‌شدهٔ وردپرس | 400 / شمارهٔ تلفن معتبر نیست |

درخواست‌های BFF اکنون Origin را از مقصد معتبر وردپرس می‌سازند. مبدأ مرورگر همچنان در مرز BFF اعتبارسنجی می‌شود. خطای Origin، خطای عمومی سیاست دسترسی و قطعی سرویس، به خطای کد پیامک یا رمز عبور تبدیل نمی‌شوند.

## معماری نشست

1. مرورگر فقط مسیرهای هم‌مبدأ `/api/auth/*` را فراخوانی می‌کند. Route Handler بدنه، مبدأ و محدودیت درخواست را بررسی می‌کند.
2. BFF کوکی‌های اصلی وردپرس را در سمت سرور دریافت می‌کند، nonce معتبر `wp_rest` را از مسیر اصلی وردپرس می‌گیرد، `sync-session` را اجرا می‌کند و هویت را با `/me` بررسی می‌کند.
3. پس از این بررسی، cookie jar و nonce با AES-256-GCM رمزنگاری و در کوکی HttpOnly همان فرانت قرار می‌گیرند. رمز عبور و کد پیامک در این کوکی ذخیره نمی‌شوند.
4. در Production کوکی `Secure`، `SameSite=Lax` و `Path=/` دارد. Domain مشترک با وردپرس تنظیم نمی‌شود. کلید ثابت `AUTH_SESSION_SECRET` باید میان تمام نمونه‌های استقرار یکسان باشد.
5. `cookies()` به‌صورت async خوانده می‌شود؛ نوشتن و پاک‌کردن کوکی در Route Handler انجام می‌شود. Server Component کوکی را تغییر نمی‌دهد.
6. Proxy فقط وجود کوکی را بررسی می‌کند. DAL و APIهای خصوصی، هویت معتبر وردپرس را بررسی می‌کنند؛ وجود کوکی مجوز دسترسی نیست.
7. درخواست‌ها و پاسخ‌های خصوصی `no-store` هستند. پاسخ کش‌شدهٔ احراز هویت، کوکی دستکاری‌شده و nonce نامعتبر پذیرفته نمی‌شوند.

پاسخ 401 با `session_expired` پیش از ورود، وضعیت مهمان در قرارداد فعلی است. کلاینت آن را به نشست `null` تبدیل می‌کند. این پاسخ به‌تنهایی خرابی ایجاد نشست را ثابت نمی‌کند.

## خروج روی Vercel

فایل محلی میان نمونه‌های Vercel مشترک و پایدار نیست. در محیط `VERCEL=1`، ابطال نشست بر عهدهٔ وردپرس است: BFF خروج را درخواست می‌کند و سپس `/me` را با همان اعتبارنامه‌های قبلی بررسی می‌کند. تنها ردشدن نشست قبلی اجازهٔ پاک‌کردن کوکی و اعلام موفقیت خروج را می‌دهد.

تشخیص Vercel به متغیر سیستم `VERCEL=1` وابسته است. گزینهٔ دسترسی به System Environment Variables در پنل این پروژه فعال بود و باید فعال بماند.

پاسخ موفق خروج به‌تنهایی کافی نیست. خطای Origin، قطعی سرویس، nonce مسدودشده یا معتبرماندن نشست قبلی، خروج موفق محسوب نمی‌شود. پاسخ استاندارد `400/0` مسیر اصلی nonce برای کاربر مهمان نیز بررسی شد؛ 403 عمومی دلیل انقضای نشست نیست.

برای اجرای تک‌سرور Node، ابطال محلی قبلی حفظ شده است. محدودکنندهٔ درخواست فعلی همچنان حافظهٔ همان پردازش است؛ محدودیت سراسری چند نمونه به کنترل مشترک در edge، وردپرس یا یک store مشترک نیاز دارد. ذخیره‌سازی قفل سبد و فایل‌های بنر موضوع جداگانه‌ای است.

## شواهد مرورگر

آزمون واقعی روی نسخهٔ محلی با `VERCEL=1` و وردپرس واقعی انجام شد. مالک شمارهٔ آزمایشی را تعیین کرد و کد را خودش در مرورگر وارد کرد. هیچ شماره، کد، رمز یا کوکی خصوصی در این گزارش ثبت نشده است.

| مرحله | نتیجه |
| --- | --- |
| ارسال کد پس از اصلاح Origin | 200؛ فرم کد نمایش داده شد |
| تأیید کد واقعی | 200 |
| درخواست‌های بعدی `/api/auth/session` | 200 |
| ورود مستقیم به `/account` | موفق |
| Reload حساب کاربری | نشست حفظ شد |
| خروج با بررسی ابطال در وردپرس | موفق |
| درخواست دوبارهٔ `/account` پس از خروج | هدایت به فرم ورود |

رفتار HTTPS و کوکی Production روی استقرار جدید Vercel پس از انتشار باید دوباره بررسی شود؛ محدودیت عدم انتشار کاربر حفظ شده است. خرید، پرداخت یا تغییر رمز انجام نشده است.

اعتبارسنجی کد: هر ۹۷ آزمون مرتبط با احراز هویت، مبدأ درخواست، حساب کاربری، سبد و تنظیمات محیط پاس شدند. lint فایل‌های تغییرکرده، بررسی TypeScript و Build نهایی Production نیز موفق بودند.
