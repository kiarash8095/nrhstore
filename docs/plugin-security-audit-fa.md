# بررسی افزونهٔ اختصاصی NRH Headless Checkout

تاریخ: ۲۰۲۶/۱۰/۳۰ تا ۲۰۲۶/۱۰/۳۱. دامنهٔ بررسی: افزونهٔ اختصاصی نسخهٔ 1.3.0 و اصلاحات آن در **1.3.1** برای استفادهٔ خصوصی همین پروژه. این گزارش تأییدیهٔ WordPress.org یا تضمین نبود همهٔ آسیب‌پذیری‌ها نیست. افزونهٔ بانکی سداد 1.3 محصول جداگانه‌ای است و بستهٔ آن در این پروژه بازنویسی نشده است.

## نتیجه و اصلاحات

نسخهٔ 1.3.0 برای نصب مستقیم توصیه نمی‌شود؛ آزمون واقعی وردپرس یک ایراد مسدودکنندهٔ سبد را نشان داد. اصلاحات زیر در 1.3.1 اعمال شده‌اند:

| مورد | اثر نسخهٔ قبلی | رفتار اصلاح‌شده |
|---|---|---|
| هدر غایب `Cart-Token` | `WP_REST_Request::get_header()` مقدار `null` می‌داد؛ مقایسه با رشتهٔ خالی درخواست مهمان و حساب را با `invalid_cart_transport` رد می‌کرد | مقدار هدر پیش از مقایسه به رشته تبدیل می‌شود؛ آزمون با خود وردپرس انجام شد |
| پایان زودهنگام قفل انتقال و تسویه | Woo ممکن بود پس از آزادشدن قفل، در shutdown نشست را دوباره بنویسد | قفل تا بعد از ذخیره‌های shutdown حفظ می‌شود؛ آزمون درخواست موازی با تأخیر عمدی shutdown انجام شد |
| ذخیرهٔ بی‌صدای ناموفق نشست | `save_data()` ووکامرس ممکن است بدون exception ناموفق شود و حتی کش را به‌روز کند | اقلام، جمع‌ها، کوپن‌ها، نشان انتقال و پیش‌نویس از جدول نشست بازخوانی می‌شوند؛ شکست SQL پاسخ موفق یا هدر تأیید قفل نمی‌گیرد |
| تغییر اقلام توسط افزونه هنگام انتقال | نشان انتقال می‌توانست همراه با سبد ناقص ذخیره شود و اجرای بعدی سبد مهمان را حذف کند | نشان `pending/complete` و اثرانگشت اقلام/تعدادها؛ سبد ناقص تکمیل تلقی نمی‌شود و مهمان محفوظ می‌ماند |
| تداخل نام قفل بین سایت‌ها | شناسهٔ یکسان کاربران در دو دیتابیس/پیشوند ممکن بود بی‌دلیل یکدیگر را مسدود کنند | نام قفل شامل اثرانگشت دیتابیس، پیشوند سایت و شناسهٔ نشست است |
| وابستگی ناقص Woo | وجود کلاس اصلی Woo برای دسترس‌بودن همهٔ APIهای مورد استفاده کافی نبود | بررسی حداقل Woo و کلاس‌های لازم؛ در نبود وابستگی، API اختصاصی غیرفعال و اعلان مدیریت نمایش داده می‌شود |
| محافظ callback قدیمی سداد | `do_action()` واقعی با آرگومان خالی اجرا می‌شود؛ محافظ قدیمی شناسهٔ سفارش URL را نادیده می‌گرفت | رشتهٔ خالی نیز آرگومان غایب تلقی می‌شود؛ درخواست واقعی به مسیر قدیمی برای سفارش NRH پیش از اجرای سداد با ۴۰۳ متوقف شد و تماس بانک تغییر نکرد |

برای پاک‌سازی سبد پس از پرداخت نیز بازخوانی ذخیره اضافه شد. اگر پاک‌سازی ذخیره نشود، وضعیت پرداختِ تأییدشده حفظ می‌شود و خطای قابل‌تکرار `cart_cleanup_unavailable` برمی‌گردد. مسیر capabilities نیز هدر خصوصی و `noindex` دارد. هیچ فایل Boom یا سداد تغییر نکرده است.

## محیط و شواهد آزمون

وردپرس از منبع رسمی دانلود و در `artifacts/plugin-audit/wordpress` نصب شد؛ دیتابیس جدا روی loopback و پورت اختصاصی، بدون اتصال به اطلاعات سایت اصلی. نسخه‌ها:

- WordPress **7.1.4**، WooCommerce **10.8.1**، PHP **8.2.12**، MariaDB **10.4.32**، Apache **2.4.58**.
- نسخهٔ رسمی Plugin Check **2.1.0** با بارگذاری `cli.php` برای بررسی‌های runtime نیز اجرا شد.
- اطلاعات دانلود و SHA-256 در `artifacts/plugin-audit/runtime-sources.json` ثبت شده‌اند.
- دو مشتری، محصول و سفارش‌های آزمون فقط در دیتابیس محلی ساخته شدند. ایمیل و درخواست‌های خارجی مسدود بودند؛ پاسخ بانک کاملاً محلی شبیه‌سازی شد.
- فایل‌های آزمایش، رمزها و دیتابیس داخل ZIP نصب قرار نمی‌گیرند.

آزمون‌های واقعی شامل سبد مهمان، Cookie و nonce حساب، دو افزودن موازی، جمع تعدادها، اجرای مجدد انتقال پس از ویرایش، جداسازی دو حساب، خطای واقعی SQL، حذف کالا توسط hook، ساخت سفارش با Store API واقعی، جلوگیری از درخواست پرداخت تکراری، رد سفارش حساب دیگر، رد callback جعلی، تأیید یک‌باره، پاک‌سازی قابل‌تکرار و قفل هنگام shutdown بودند. گزارش‌ها: `artifacts/plugin-audit/integration-CPT.json` و `artifacts/plugin-audit/integration-HPOS.json`. **این آزمون سازگاری با کد داخلی Boom نیست.**

آزمون‌های مستقل PHP نیز با `node wordpress/tests/run.cjs` اجرا شدند؛ شامل تزریق ورودی، CSRF، توکن جعلی، مالکیت سفارش، قطع بانک، مبلغ/ارز نامعتبر، شکست ذخیره، محافظت از callback قدیمی و محدودیت موجودی/رزروشده هستند. نتیجه: **۶۴ تست PHP، ۱۰۱ تست BFF/قفل Node و ۲۵ تست محیط؛ همگی موفق (۱۹۰ تست)**. علاوه بر آن **۱۹ سناریو در CPT و همان ۱۹ سناریو در HPOS** با WordPress و دیتابیس واقعی موفق شدند. آزمون واقعی محافظ callback قدیمی نیز پس از اصلاح پاسخ ۴۰۳ گرفت؛ شواهد در `artifacts/plugin-audit/legacy-guard.json` هستند. بانک در همهٔ این آزمون‌ها شبیه‌سازی شده است. build و مرورگر production در مرحلهٔ پیشین موفق بودند؛ در این مرحله کد اجرایی Next تغییر نکرد و build دوباره اجرا نشد.

اثر روی مسیر عمومی نیز با فعال/غیرفعال‌کردن افزونه در نصب محلی بررسی شد. assetهای صفحهٔ اصلی، canonical، robots و JSON محصولات عمومی یکسان ماندند. برای ۸ درخواست کاتالوگ در هر حالت، p50 بدون/با افزونه **۸۰۶/۷۹۶ میلی‌ثانیه** و p95 **۹۴۹/۹۵۱ میلی‌ثانیه** بود؛ این نمونهٔ کوچک افت آشکاری نشان نداد و تضمین کارایی production یا آزمون بار نیست. در سناریوهای CPT، p50/p95 دریافت سبد **۹۶۳/۱۶۸۷ میلی‌ثانیه** بود؛ این زمان کل پشتهٔ محلی با debug فعال است، نه سربار خالص افزونه. گزارش: `artifacts/plugin-audit/public-impact.json`.

## امنیت و معماری

- مسیرهای خصوصی علاوه بر nonce به هویت احراز‌شدهٔ وردپرس و مالکیت حساب/سفارش تکیه دارند. nonce به‌تنهایی احراز هویت یا جلوگیری از بازپخش نیست؛ این موضوع در [مستندات WordPress](https://developer.wordpress.org/apis/security/nonces/) تصریح شده است.
- Cart-Token فقط برای مهمان استفاده می‌شود؛ انتقال، حساب عددی را به‌عنوان مهمان نمی‌پذیرد. مشتری واردشده از Cookie و nonceهای بومی WP/Store API استفاده می‌کند.
- قیمت، موجودی، کوپن، ارسال، سفارش و وضعیت پرداخت در Woo می‌مانند. مرورگر کلید پذیرنده یا دسترسی دیتابیس دریافت نمی‌کند. ارتباط خروجی افزونه محدود به آدرس ثابت HTTPS سداد، با بررسی TLS، بدون دنبال‌کردن redirect و با محدودیت اندازه/زمان پاسخ است.
- callback به سفارش، توکن و کلید تصادفیِ ذخیره‌شده متصل است؛ پرداخت تنها پس از Verify معتبر ثبت می‌شود. درخواست تکراری همان پرداخت را از نو آغاز نمی‌کند.
- queryهای قفل و بازخوانی نشست آماده‌سازی شده‌اند. کش‌کردن نتیجهٔ قفل یا اثبات ذخیره صحیح نیست؛ این queryها عمداً به دیتابیس می‌روند.
- فایل‌های بسته شامل کد اجرایی دانلودشونده، telemetry، cron اختصاصی، جدول جدید، asset فرانت یا تنظیم robots/canonical عمومی نیستند. غیرفعال‌سازی افزونه سفارش‌ها و اطلاعات کاربران را حذف نمی‌کند.
- در این معماری Next فقط BFF است. به حافظه یا فایل مشترک Vercel وابسته نیست؛ هماهنگی روی وردپرس انجام می‌شود.

## محدودیت‌های سازگاری، سئو و هاست

قالب **Boom 3.0.0** طبق اعلام مالک فقط روی هاست است و سورس آن در اختیار این بررسی نبود. بنابراین هماهنگی با hookهای داخلی قالب، افزونه‌های فعال، کش واقعی و کل جریان پیامک روی همان نصب هنوز قطعی نیست. اگر قالب نشست را پیش از قفل بارگذاری کند، افزونه برای جلوگیری از خرابی داده با `cart_session_loaded_early` یا `account_session_loaded_early` متوقف می‌شود؛ حذف این کنترل راه‌حل تداخل نیست.

قفل‌ها advisory و وابسته به یک اتصال دیتابیس هستند. تمام درخواست‌های مشارکت‌کننده باید به همان سرور دیتابیس مشترک برسند. میزبان Next می‌تواند تغییر کند، اما هر هاست دلخواه با هر نوع دیتابیس/پراکسی تضمین نمی‌شود. رفتار `GET_LOCK` و ضرورت نام اختصاصی برنامه در [مستندات MariaDB](https://mariadb.com/docs/server/reference/sql-functions/secondary-functions/miscellaneous-functions/get_lock) توضیح داده شده است. APIها یا کدهای وردپرس که هدر پروتکل ندارند، قفل‌های این رابط را رعایت نمی‌کنند؛ این بررسی بر فرض اعلام‌شدهٔ انجام تمام خریدها از Next استوار است.

صفحات عمومی، sitemap، canonical و تنظیمات سئوی قالب در کد افزونه بازنویسی نمی‌شوند؛ `noindex` به API خصوصی محدود است. این نتیجه به معنای تضمین رتبهٔ جست‌وجو یا سازگاری با تمام افزونه‌های سئو نیست. اندازه‌گیری محیط محلی معادل سرعت هاست نهایی نیست؛ کش CDN/WP باید تمام مسیرهای شخصی cart/checkout/auth و `/nrh/v1/*` خصوصی را کنار بگذارد. مسیر عمومی موجود `/nrh/v1/filters` نباید بی‌دلیل خصوصی شود.

## نتیجهٔ Plugin Check و اعتبار

خروجی کامل در `artifacts/plugin-audit/plugin-check-full.txt` نگهداری می‌شود. افزونه در مخزن WordPress.org منتشر یا توسط آن تأیید نشده است. [خود Plugin Check](https://wordpress.org/plugins/plugin-check/) نیز بررسی خودکار را جایگزین بازبینی دستی نمی‌داند.

خروجی نهایی ابزار **۶ خطای فرادادهٔ انتشار عمومی** و **۲۱ هشدار** دارد: یک هشدار طول توضیح README و ۲۰ هشدار query مستقیم/بدون کش برای ۱۰ فراخوانی ضروری دیتابیس. هیچ‌کدام از این هشدارها به‌صورت کلی غیرفعال نشده‌اند. بنابراین نتیجهٔ ابزار «بدون خطا» گزارش نمی‌شود؛ فهرست دقیق در `artifacts/plugin-audit/plugin-check-summary.json` موجود است.

خطاهای فرادادهٔ انتشار عمومی مانند مجوز اعلام‌نشده، Stable Tag، Tested up to و متن فارسی README باید از ایراد امنیتی زمان اجرا تفکیک شوند؛ برای استفادهٔ خصوصی، مجوز انتشار عمومی از طرف مالک فرض یا تعیین نشده است. هشدارهای query مستقیم/بدون کش باید با دلیل فنی بالا خوانده شوند، نه اینکه صرفاً مخفی شوند. خواندن شناسه در محافظ callback قدیمی عمداً nonce نمی‌خواهد، چون فقط درخواست را رد می‌کند و هیچ دسترسی/پرداختی اعطا نمی‌کند؛ این استثنای تک‌خطی مستند شده است. افزودن شرط nonce به این محافظ، درخواست جعلی بدون nonce را از محافظت خارج می‌کرد. ورودی آن پاک‌سازی و سپس با الگوی عددی سخت‌گیرانه بررسی می‌شود. خروجی ابزار به‌تنهایی گواه «امنیت کامل» نیست.

در منبع رسمی سداد 1.3 که برای آزمایش نصب شد، هشدارهای PHP 8.2 دربارهٔ dynamic property دیده شد. این هشدارها از افزونهٔ سداد بودند؛ به معنای بررسی یا تأیید همهٔ امنیت آن نیستند. نسخهٔ نصب‌شده روی هاست با این فایل تطبیق بیتی نشده است. کلیدها و توکن‌ها نباید در لاگ عمومی یا صفحهٔ خطا نمایش داده شوند.

## کار باقی‌مانده روی هاست

۱. پشتیبان فایل‌ها/دیتابیس و نصب **1.3.1** در staging با همان Boom، سداد و افزونه‌های فعال. ورود واقعی، انتقال دو سبد، تغییر پنل و جداسازی دو حساب آزمایش شود.

۲. پشتیبانی هاست از نسخه‌های لازم، HTTPS، ارتباط خروجی سداد و `GET_LOCK` روی یک primary مشترک تأیید شود؛ در هاست Node نیز اجرای Next/BFF و متغیرهای امن لازم است. پلن نهایی هنوز مشخص نشده است.

۳. مبدأ `NRH_HEADLESS_FRONTEND_URL` و استثنای کش خصوصی تنظیم شود؛ سپس خرید کم‌مبلغ واقعی، بازگشت بانک، تازه‌سازی/بازگشت تکراری، موجودی و نمایش سفارش/سبد در پنل کنترل شوند. تأیید واقعی بانک با mock جایگزین نشده است.

هیچ نصب، commit، push یا انتشار روی سایت اصلی در این بررسی انجام نشده است.

بستهٔ نهایی: `artifacts/wordpress/nrh-headless-checkout-1.3.1.zip`؛ شامل ۶ فایل افزونه و بدون ابزار/دیتابیس/اطلاعات آزمون. SHA-256: `ba368aeedd0f9950367615f6e69b83996396c5218790cab5ccbbcb62edee6d95`. تمام فایل‌های ZIP با سورس تطبیق داده شدند؛ manifest کنار بسته موجود است.
