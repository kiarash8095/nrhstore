# بررسی development و production - ۲۰۲۶/۱۰/۲۳

## علت اصلی حذف دسته‌های هدر

`StoreHeader` خروجی واقعی ووکامرس را با پنج slug ثابت فیلتر می‌کرد. در پاسخ عمومی وردپرس، شناسه دسته‌ها ثابت مانده ولی چهار slug تغییر کرده است:

| شناسه | مقدار قدیمی فرانت | مقدار فعلی وردپرس |
| --- | --- | --- |
| 55 | `laptop` | `laptop` |
| 365 | `hardware` | `computer-hardware` |
| 57 | `edari` | `printers-scanners` |
| 58 | `network` | `network-equipment` |
| 59 | `accessory` | `accessories` |

بنابراین شرط قبلی فقط لپ‌تاپ را نگه می‌داشت. این خطا مختص production نیست؛ با داده فعلی در یک اجرای تازه development هم وجود داشت. متفاوت‌بودن نسخه bundle، داده کش‌شده یا وضعیت اجرای قبلی می‌تواند تفاوت ظاهری ایجاد کند، اما این موارد برای محیط قبلی کاربر اثبات نشده‌اند.

در بررسی تنظیمات همین دستگاه، هر دو حالت `.env.local` و همان آدرس بک‌اند را مصرف کردند؛ تفاوت مبدأ API علت مشاهده‌شده نبود.

## اصلاحات

1. مرجع مشترک `features/categories/constants/navigation.ts` برای شناسه، ترتیب و alias دسته‌ها اضافه شد. هدر دسته‌های واقعی را بر اساس شناسه پایدار انتخاب می‌کند و نام و URL همان پاسخ ووکامرس را حفظ می‌کند.
2. منو و آیکن‌ها از همان نگاشت استفاده می‌کنند. سابقاً شناسه‌ها در چند فایل تکرار و حتی برای لوازم جانبی ناسازگار بودند.
3. نشانی قدیمی دسته‌های اصلی به دسته واقعی resolve و به URL canonical هدایت می‌شود؛ مثلاً `network` به `network-equipment`. شماره صفحه حفظ می‌شود. این کار لینک‌های قدیمی خانه و فوتر را هم پوشش می‌دهد.
4. مقایسه اشتباه `NEXT_PUBLIC_BASE_URL === 'production'` حذف و سیاست خواندن عمومی دسته‌ها با TTL برابر ۳۰۰ ثانیه یکسان شد. آدرس API نباید به‌عنوان نام محیط استفاده شود.
5. وقتی شناسه دسته داریم، آن را با slug قدیمی در درخواست upstream intersect نمی‌کنیم. اندازه صفحه helperهای دسته و زیردسته نیز با client هماهنگ شد.
6. query key دسته‌های اصلی اکنون شناسه‌ها را هم دارد؛ کلید زیردسته‌ها میان مصرف‌کننده‌ها یکسان شد. signal لغو Query به Axios می‌رسد.
7. خطای زیردسته با حالت خالی اشتباه گرفته نمی‌شود؛ پیام و دکمه تلاش دوباره وجود دارد. لینک `/undefined` برای دسته ناموجود ساخته نمی‌شود و دریافت اولیه منو تا بازشدن آن شروع نمی‌شود.
8. در اولین build آزمایشی، prerender نقشه سایت با timeout وردپرس شکست خورد. `sitemap` اکنون با `connection()` هنگام درخواست تولید می‌شود؛ کش ۳۰۰ثانیه‌ای خواندن کاتالوگ باقی می‌ماند. این اصلاح مانع همان وابستگی sitemap به پاسخ کامل فروشگاه در زمان build است؛ به معنی حذف تمام ارتباطات شبکه در build نیست.

## تفاوت‌های واقعی دو حالت

| موضوع | development | production |
| --- | --- | --- |
| اجرا | `next dev`، کامپایل درخواستی و HMR | خروجی `next build` و سپس `next start` |
| متغیر عمومی | با اجرای توسعه خوانده می‌شود | مقدار `NEXT_PUBLIC_*` در bundle زمان build تثبیت می‌شود |
| کش سرور | HMR و hard refresh می‌توانند رفتار دریافت را تغییر دهند | TTL و خروجی prerender پایدارتر و قابل مشاهده‌ترند |
| هشدارها | هشدارهای تصویری و توسعه در مرورگر بیشترند | نبود هشدار توسعه، اثبات نبود مسئله نیست |
| کوکی خصوصی | مطابق تنظیم محیط | Secure و HTTPS برای دامنه واقعی الزامی باقی مانده است |

برای رفع منو، هیچ کنترل احراز هویت، nonce، مالکیت سفارش یا ویژگی Secure کوکی غیرفعال نشد.

## روش مقایسه

دو سرور مجزا با همان کد و بک‌اند و خروجی‌های مستقل اجرا شدند تا پوشه فعال `.next` با اجرای build بازنویسی نشود. تنظیم اختیاری `NRH_NEXT_DIST_DIR` اضافه شده است؛ در نبود آن رفتار قبلی `.next` برقرار است.

```powershell
$env:NRH_NEXT_DIST_DIR = '.next/environment-parity/production'
npm run build
npm run start -- --port 4111
```

در ترمینال جدا:

```powershell
$env:NRH_NEXT_DIST_DIR = '.next/environment-parity/development'
npm run dev -- --port 4112
```

تست `features/categories/tests/navigation.browser.cjs` با `CATEGORIES_TEST_URL` و `CATEGORIES_TEST_MODE` برای هر دو سرور قابل اجراست. مانند سایر تست‌های مرورگر پروژه، Playwright باید از طریق `PLAYWRIGHT_MODULE` در دسترس باشد. آزمون خواندن واقعی دسته‌ها، ترتیب و آیکن‌ها، زیردسته‌ها، هدایت alias و بازیابی خطای شبیه‌سازی‌شده را بررسی می‌کند. auth و cart در مرورگر این آزمون intercept می‌شوند؛ ارسال پیامک، تغییر سبد، سفارش و پرداخت واقعی انجام نمی‌شود.

## شواهد بررسی

- ۳۲ تست کاتالوگ، مسیریابی و محیط موفق شدند؛ ۵ تست جدید مربوط به نگاشت دسته و برابری تنظیمات دو حالت‌اند.
- build با Turbopack نسخه Next.js نصب‌شده `16.2.12` پس از اصلاح sitemap موفق شد و بررسی TypeScript آن نیز گذشت.
- lint خطای تازه ندارد؛ دو هشدار قبلی `img` در جست‌وجو باقی‌اند.
- گزارش‌های مرورگر و تصویر منوی هر حالت در `artifacts/environment-parity` قرار می‌گیرند. نتیجه معتبر، فایل `development-results.json` یا `production-results.json` بدون کلید `error` است؛ `browserErrors` باید خالی باشد.

در اجرای نهایی هر دو گزارش موفق بودند و مقایسه ماشینی آن‌ها برابری داده را تأیید کرد:

| دسته | زیردسته در development | زیردسته در production |
| --- | --- | --- |
| لپ‌تاپ | ۰ | ۰ |
| کامپیوتر و قطعات | ۲ | ۲ |
| ماشین‌های اداری | ۶ | ۶ |
| تجهیزات شبکه | ۵ | ۵ |
| لوازم جانبی | ۱۱ | ۱۱ |

خالی‌بودن زیردسته لپ‌تاپ در پاسخ فعلی ووکامرس واقعی است، نه خطای بارگذاری. تست آیکن‌ها، هدایت لینک قدیمی شبکه، نمایش خطای کنترل‌شده و بازیابی با تلاش دوباره در هر دو حالت موفق شد و خطای JavaScript هر دو صفر بود.

دامنه این مقایسه، پیکربندی محیط، دریافت داده عمومی، مگامنو، مسیر دسته، کش و ساخت خروجی است. این گزارش ادعای آزمون دوباره ورود واقعی، درگاه بانکی، نصب PHP یا همه فیچرهای خصوصی روی هاست production ندارد.

پس از دریافت اصلاحات باید خروجی پیشین را دوباره build و فرایند `start` را با همان تنظیمات آن build راه‌اندازی کرد. تغییر فایل TypeScript به‌تنهایی bundle قدیمی سرور production را عوض نمی‌کند.
