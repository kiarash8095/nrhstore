# داشبورد و دسترسی حساب کاربری

فیچر `account` در نسخه فعلی یک داشبورد ساده و محافظت‌شده است: نام کاربر، شماره ماسک‌شده یا ایمیل و دکمه خروج را نشان می‌دهد. فهرست سفارش، ویرایش پروفایل، مدیریت آدرس و پیگیری سفارش هنوز در این فیچر ساخته نشده‌اند.

**مسیر درخواست صفحه**

```text
GET /dashboard
  → Proxy: آیا کوکی وجود دارد؟
  → AccountPage روی سرور
  → requireUser('/dashboard')
  → اعتبار کوکی و ابطال محلی + بررسی /me وردپرس
  → DTO کاربر → HTML داشبورد
```

[proxy.ts](D:/Projects2/nrh_store_nextjs/proxy.ts) اگر کوکی نباشد به `/?auth=login&next=...` هدایت می‌کند. هدف، بازکردن مودال ورود و حفظ مقصد است. اگر کوکی وجود داشته باشد، هنوز ممکن است جعلی یا منقضی باشد؛ تصمیم معتبر در DAL انجام می‌شود. همه این مسیرها داخل Next هستند.

[AccountPage](D:/Projects2/nrh_store_nextjs/features/account/components/AccountPage.tsx) از `requireUser` استفاده می‌کند. DAL دارای `server-only` است و با `React.cache` فراخوانی تکراری یک رندر را کم می‌کند. در رندر Server Component، فقط نشست خوانده و بررسی می‌شود؛ نوشتن کوکی در این مسیر انجام نمی‌گیرد. خطای backend هم نباید به هویت ساختگی تبدیل شود.

**چرا `useAuth` به‌تنهایی کافی نیست؟**

state مرورگر برای تغییر آیکن هدر یا نمایش نام مناسب است. کاربر می‌تواند JavaScript مرورگر را تغییر بدهد؛ داده خصوصی باید پیش از دریافت روی سرور مجوز بخواهد. به همین دلیل layout حساب فقط `noindex` تعیین می‌کند و بررسی اصلی روی صفحه نزدیک داده است. matcher شامل `/account` هم هست، ولی Route حساب جدا در نسخه فعلی وجود ندارد.

**خروج چگونه هماهنگ می‌شود؟**

[LogoutButton](D:/Projects2/nrh_store_nextjs/features/auth/components/LogoutButton.tsx) دکمه را مشغول می‌کند، اکشن خروج را اجرا و پس از موفقیت `/` همین سایت را باز می‌کند. اکشن، API خروج را صدا می‌زند، وضعیت مرورگر و کش Query را پاک و خبر خروج را برای تب‌های دیگر ارسال می‌کند. حذف ظاهر کاربر به‌تنهایی logout نیست؛ ابطال سروری در [راهنمای ورود](D:/Projects2/nrh_store_nextjs/docs/auth-learning-fa.md) توضیح داده شده است.

**اگر بخواهم سفارش‌ها را بعداً اضافه کنم**

این بخش نقشه توسعه است و در کد فعلی وجود ندارد:

1. قرارداد واقعی دریافت سفارش و مجوز آن را مشخص کن.
2. هویت را در Route Handler یا تابع سروری دریافت کن؛ شناسه کاربرِ فرستاده‌شده از مرورگر را مرجع مالکیت قرار نده.
3. مجوز دسترسی به همان سفارش را کنترل و DTO محدود برای UI بساز.
4. فهرست، صفحه‌بندی، حالت خالی، خطا و جزئیات سفارش را جدا طراحی کن.
5. کلید کش را با هویت کاربر جدا کن و در ورود/خروج اجازه نمایش داده حساب قبلی نده.

**تمرین:** تست DAL را بخوان و توضیح بده چرا وجود کوکی به‌تنهایی کافی نیست. در مرورگر مهمان `/dashboard` را باز کن و مقصد `next` را دنبال کن. آزمون `test:auth:browser` حالت مهمان و کوکی جعلی را پوشش می‌دهد؛ حالت نشست واقعی تنظیم اختیاری جدا دارد و هنگام خروج همان نشست را باطل می‌کند.
