# بررسی امکان حذف رابط اختصاصی سبد و پرداخت

تاریخ: ۲۰۲۶-۱۰-۳۰. دامنه: بررسی و آزمون؛ کد اجرایی، افزونه نصب‌شده و deployment تغییر نکردند.

**نتیجه: جایگزینی کامل هر پنج مرحله، با تمام شروط اعلام‌شده و صرفاً APIهای فعلی، فعلاً قابل تأیید نیست. دو بخش اول قابل انجام‌اند؛ هم‌زمانی و انتقال قابل‌بازیابی نیازمند راهکار اثبات‌شده‌اند و مسیر پرداخت نسخه رسمی سداد ۱٫۳ با خروج مستقیم از Next به بانک مطابقت ندارد. این نتیجه الزام به استفاده از همین افزونه اختصاصی نیست؛ قابلیت‌های جایگزین باید در راه دیگری فراهم شوند.**

## شروط صریح مالک پروژه

- تمام تجربه خرید و تسویه در Next باشد؛ مشتری فقط برای پرداخت به بانک منتقل شود.
- سبد مهمان پس از ورود به سبد حساب منتقل و با آن ادغام شود.
- تعداد کالای مشترک جمع شود، مثلاً حساب ۲ و مهمان ۳، نتیجه ۵؛ تکرار انتقال نباید آن را ۸ کند.
- فقط APIهای فعلی وردپرس، بدون PHP جدید، Redis یا دیتابیس جدا.
- اطلاعات در دیتابیس فعلی وردپرس بمانند؛ فروشگاه قالب وردپرس برای خرید هم‌زمان مشتریان استفاده نشود.
- Vercel فعلاً محیط آزمایشی است. پلن دقیق میزبانی نهایی برای ارزیابی قابلیت‌های Node مشخص نشده است.

## نتیجه پنج مرحله

| مرحله | نتیجه | شاهد و محدودیت |
| --- | --- | --- |
| BFF در Next | قابل انجام و در پروژه موجود | مرورگر API هم‌مبدأ را صدا می‌زند؛ کوکی احراز هویت رمزگذاری‌شده/HttpOnly و cookie jar سرور برقرارند. حذف رابط PHP لزوماً به تغییر این قرارداد نیاز ندارد. |
| عملیات عادی سبد با Store API | قابل انجام؛ مسیر مهمان واقعاً آزموده شد | دریافت، افزودن، تغییر تعداد، حذف، کوپن، آدرس و روش ارسال در فهرست زنده وجود دارند. آزمون‌های سری مهمان قبلی موفق بودند؛ این بررسی تأیید تازه‌ای برای سبد واقعی حساب یا همهٔ محصولات/افزونه‌های محصول صادر نمی‌کند. |
| هماهنگی درخواست‌ها بدون فایل Vercel | با قیود فعلی حل اثبات‌شده‌ای نداریم | گم‌شدن افزودن هم‌زمان روی API واقعی بازتولید شد. API ثبت‌شده‌ای برای قفل سبد یا نوشتن مشروط بر نسخه مشاهده نشد. صف مرورگر یا حافظه یک Function بین همه نمونه‌ها مشترک نیست. |
| ادغام با جمع تعداد و مقاومت در برابر قطع ارتباط | پشتیبانی سرور فعلاً نامعلوم؛ تأیید نشده | Boom مسیر `sync-cart` دارد و JS عمومی بدنه را نشان می‌دهد، اما رفتار سروریِ ادغام، عدم تکرار و شکست میان مراحل مشخص نیست. فراخوانی چند `add-item` به‌خودی‌خود انتقال یک‌باره ایجاد نمی‌کند. |
| پرداخت Next → بانک با سداد فعلی | با قرارداد رسمی نسخه ۱٫۳ مطابقت ندارد | روش `process_payment` صفحه `order-pay` وردپرس را برمی‌گرداند؛ دریافت توکن بانک در hook رسید انجام می‌شود. بازگشت موفق هم به صفحه نتیجه وردپرس است. |

## بررسی API واقعی سایت

فهرست زنده [REST API همین فروشگاه](https://nrhstore.ir/wp-json/) و OPTIONS مسیرهای مربوط بررسی شدند. نسخه‌های `wc/store` و `wc/store/v1`، مسیرهای سفارش `wc/v3` و مسیرهای Boom وجود دارند.

این فهرست، REST routeهای ثبت‌شده است؛ همهٔ توابع PHP، Woo AJAX و hookهای پرداخت افزونه‌ها در آن نمایش داده نمی‌شوند. نبود اطلاعات `args` برای یک route هم قرارداد کامل بدنه/رفتار آن را ثابت نمی‌کند.

- `GET /wc/store/v1/cart` و مسیرهای افزودن، حذف، تعداد، کوپن، مشتری و ارسال فعال‌اند.
- `POST /boom/v1/sync-cart` فعال است، ولی هم REST index و هم OPTIONS آن `args` خالی دارند.
- JS عمومی فعلی Boom بدنهٔ `{ items: [...] }` با `product_id`، `quantity` و برای محصول متغیر `variation_id` و دادهٔ خدمات را می‌فرستد؛ پس از پاسخ موفق کاربر را به `/checkout` وردپرس می‌برد. این فقط قرارداد قابل مشاهدهٔ کلاینت است و رفتار ذخیره/قفل سرور را اثبات نمی‌کند.
- مسیر `GET /wc/v3/payment_gateways/melli_pay` بدون احراز هویت ۴۰۱ داد و تنظیمات را افشا نکرد. این API برای مشاهده/تنظیم درگاه است، نه گرفتن توکن یا تأیید تراکنش. [مستندات Payment Gateways](https://developer.woocommerce.com/docs/apis/rest-api/v3/payment-gateways/).
- مسیرهای اختصاصی checkout/merge رابط NRH در فهرست زنده مشاهده نشدند؛ `nrh/v1/filters` وجود دارد.

فهرست بدون اطلاعات خصوصی در `artifacts/cart-without-plugin-audit/all-payment-cart-routes.json` و قراردادهای انتخاب‌شده در `public-api-contracts.json` ذخیره شدند.

## بازتولید هم‌زمانی با سبد مهمان واقعی

در یک سبد مهمان تازه و مستقل، یک واحد محصول ساده ۱۶۵۹ اضافه شد. سپس دو افزودن یک‌واحدی هم‌زمان مستقیم به Store API ارسال شدند:

- هر دو پاسخ **۲۰۱ موفق** بودند.
- هر دو پاسخ تعداد **۲** را نشان دادند.
- بازخوانی با URL یکتا، بعد از ۵۰۰ میلی‌ثانیه، تعداد ذخیره‌شده **۲** بود؛ انتظار **۳** بود.
- پاسخ cache hit نبود. سبد در پایان حذف و بازخوانی صفر تأیید شد.

گزارش: `artifacts/cart-without-plugin-audit/native-cart-concurrency-results.json`؛ اسکریپت بازتولید: `native-cart-concurrency.cjs` همان پوشه.

این آزمون ثابت می‌کند خود API خام روی فروشگاه فعلی برای این سناریو از گم‌شدن تغییر جلوگیری نمی‌کند. فعال‌نبودن فروشگاه قالب برای مشتریان، دامنه هماهنگی را ساده‌تر می‌کند، اما چند تب، چند دستگاه و چند workerِ BFF همچنان درخواست هم‌زمان ایجاد می‌کنند.

کد رسمی WooCommerce 10.8.1 نیز نشست توکن را ابتدا می‌خواند و در shutdown می‌نویسد؛ نوشتن، جایگزینی مقدار کامل نشست است. [SessionHandler رسمی](https://github.com/woocommerce/woocommerce/blob/10.8.1/plugins/woocommerce/src/StoreApi/SessionHandler.php). فایل readme عمومی سایت 10.7.0 و URL فایل‌های JS عدد 10.8.1 نشان می‌دهند؛ نسخه دقیق PHP نصب‌شده از این دو نشانه قطعی اعلام نشده است. نتیجه آزمون زنده به حدس نسخه وابسته نیست.

صف یک Node دائمی می‌تواند درخواست‌های همان فرایند را مرتب کند؛ برای تعیین کفایت آن باید مدل اجرا، تعداد workerها، داده پایدار و بازیابی درخواست مبهم مشخص شوند. لغو fetch در Next به معنی توقف قطعی نوشتن PHP نیست. Redis هم در صورت مجازشدن، صرف نامش راه‌حل کامل نیست؛ قفل دارای مهلت و بازیابی درست لازم است. [محدودیت مدت اعتبار قفل Redis](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

## انتقال سبد و جمع تعداد

برای انتقال امن باید هم‌زمان هویت حساب و سبد مهمان تأیید شود، قیمت/موجودی/تنوع را Woo محاسبه کند، مجموع تعدادها فقط یک‌بار اعمال شود و حذف مهمان پس از ذخیره قطعی حساب صورت گیرد.

مثال شکست: حساب ۲ و مهمان ۳ است. افزودن ۳ موفق می‌شود اما پاسخ گم می‌شود. اگر انتقال دوباره جمع کند، تعداد ۸ می‌شود. نوشتن مقدار نهایی ۵ نیز بدون شناخت پیشرفت عملیات و هماهنگی با تغییرات جدید حساب، پاسخ کامل همهٔ شکست‌ها نیست. به قرارداد قابل بازیابی و وضعیت پایدار عملیات نیاز است؛ امنیت با چند فراخوانی متوالی API یا guard رابط کاربر اثبات نمی‌شود.

در API عمومی مشاهده‌شده، شناسه انتقال/تعهدی برای انجام یک‌باره یا ادغام اتمیک مستند نشده است. این به معنی اثباتِ نبودن چنین کدی در Boom نیست؛ سورس سرور یا مستندات معتبر آن در دسترس این بررسی نبود و هیچ رفتار سروری حدس زده نشده است. مسیر `cart/extensions` هم فقط به callback ثبت‌شده در PHP ارجاع می‌دهد و به‌تنهایی عملیات ادغام دلخواه اضافه نمی‌کند.

رابط محلی فعلی `class-nrh-cart-session.php` برای کالای مشترک تعداد مهمان را جایگزین می‌کند؛ مطابق خواسته جدید باید تغییر کند. چون درخواست فعلی بررسی است، این رفتار در این مرحله بازنویسی نشد.

## سداد رسمی ۱٫۳ و مرز تأیید امنیت

سورس نسخه ۱٫۳ از [مخزن رسمی معرفی‌شده سداد](https://github.com/SadadPsp-Lab/WooCommerce) دریافت شد؛ شناسه درگاه `melli_pay` است. کد `process_payment` آدرس پرداخت وردپرس را می‌دهد و hook رسید، درخواست بانک و فرم انتقال را می‌سازد. Store API در حالت legacy همان روش پرداخت را اجرا می‌کند و خودکار لینک مستقیم بانک ایجاد نمی‌کند. [کد سداد](https://github.com/SadadPsp-Lab/WooCommerce/blob/master/index.php)، [پشتیبانی legacy ووکامرس](https://developer.woocommerce.com/docs/block-development/extensible-blocks/cart-and-checkout-blocks/checkout-payment-methods/payment-method-integration/#processing-payments-legacy-support).

آزمون محلی فقط همان متد بدون تغییر را با Woo order double اجرا کرد و بازگشت `order-pay` را تأیید کرد؛ افزونه بارگذاری/نصب نشد و سفارشی در فروشگاه ایجاد نشد. گزارش و hash سورس: `artifacts/cart-without-plugin-audit/sadad-contract-results.json`.

در همین سورس رسمی، بررسی گواهی TLS در cURL غیرفعال است؛ همچنین اتصال توکن و شناسه تراکنش تأییدشده به اطلاعات پرداخت ذخیره‌شدهٔ همان سفارش، پیش از `payment_complete` دیده نمی‌شود. این‌ها یافته‌های بررسی کد رسمی‌اند؛ تطابق بایت‌به‌بایت با فایل نصب‌شده و بهره‌برداری روی فروشگاه بررسی نشده است. بنابراین امنیت مسیر قدیمی هم بدون بررسی بیشتر تأیید نمی‌شود.

## نتیجه تصمیم

با قیود فعلی، حذف رابط و اتصال مستقیم به همین APIها، جایگزین کامل و تأییدشده برای فرایند موردنظر نیست. انتقال تجربه خرید به هاست دائمی، محدودیت فایل Vercel را تغییر می‌دهد؛ قابلیت پرداخت مستقیم و انتقالِ یک‌بارهٔ جمع تعداد را خودبه‌خود به API وردپرس اضافه نمی‌کند.

برای پاسخ مثبت، باید API موجود Boom تضمین‌های انتقال/بازیابی را واقعاً داشته باشد و مسیر پرداخت موجود لینک بانک و بازگشت مناسب Next فراهم کند، یا اجازهٔ افزودن همین قابلیت‌های محدود سمت سرور داده شود. ارائهٔ آن‌ها الزاماً به همین بستهٔ افزونه NRH وابسته نیست. اتصال جدید BFF به API بانک نیز طراحی پرداخت دیگری است و در محدوده «فقط APIهای فعلی وردپرس» محسوب نمی‌شود.

در این بررسی درخواست checkout یا پرداخت، تماس با بانک و پیامک انجام نشد. هیچ افزونه‌ای نصب/حذف و هیچ کدی commit، push یا deploy نشد. تغییرات اجرایی آماده‌شده در مرحله قبلی حفظ شدند؛ این مرحله فقط شواهد و گزارش بررسی را اضافه کرد.
