# راه‌اندازی قابل تکرار و آمادگی انتشار

> یادداشت پاک‌سازی ۲۰۲۶/۱۰/۲۳: گزارش‌ها و تصاویر خام قدیمی با درخواست مالک پروژه حذف شدند. نتایج تاریخی متن این سند حفظ شده‌اند؛ پیوندهای artifacts قدیمی ممکن است موجود نباشند. شواهد فعلی و مرز آزمون زنده در [گزارش امنیت و باگ](security-audit-fa.md) آمده‌اند.


این گزارش مربوط به اصلاحات و آزمون‌های ۲۰۲۶/۱۰/۱۹ است. انجام آزمون واقعی OTP و سبد به معنی آماده‌بودن پرداخت و همهٔ زیرساخت‌های انتشار نیست.

## اجرای پروژه روی دستگاه جدید

```sh
npm ci
npm run dev
```

`predev` با ابزار `scripts/environment.cjs` کلید محلی ناموجود را یک‌بار تولید و در `.env.local` خارج از Git ذخیره می‌کند. کلید ۳۲ بایت تصادفی است که به‌صورت ۶۴ کاراکتر hex ذخیره می‌شود. اجرای دوباره و اجرای هم‌زمان setup کلید را نمی‌چرخانند. مقادیر معتبر موجود حفظ می‌شوند. فقط محیط توسعه اجازهٔ این آماده‌سازی را دارد.

ورود در هر نصب مستقل با OTP واقعی وردپرس انجام می‌شود؛ لازم نیست کلید محیط production را به لپ‌تاپ‌های توسعه منتقل کنی. کاربری که یک استقرار مشترک را با چند دستگاه باز می‌کند، با همان سرور و کلید ثابت آن استقرار کار می‌کند. کوکی‌های مرورگرها مستقل‌اند؛ ورود روی دستگاه دوم نیاز به احراز هویت همان دستگاه دارد.

## کنترل تنظیمات و خطاها

`npm run setup:env` آماده‌سازی توسعه و `npm run doctor` بررسی تنظیمات، پوشه‌های قابل‌نوشتن، مسیرهای واقعی احراز هویت و صدور Cart-Token ووکامرس را اجرا می‌کنند. doctor کد پیامکی نمی‌فرستد و کالایی اضافه نمی‌کند.

پیش از ارسال OTP یا ساخت نشست، وجود کلید معتبر بررسی می‌شود. خرابی تنظیمات با ۵۰۳ و `configuration_error` گزارش می‌شود؛ مقدار کلید به مرورگر یا لاگ نمی‌رود. کاربر مهمان همچنان از `/api/auth/session` پاسخ ۴۰۱ می‌گیرد. راز نشست فقط در سرور و برای رمزنگاری AES-256-GCM استفاده می‌شود؛ توکن‌های ووکامرس در کوکی HttpOnly هستند.

## شواهد واقعی این نوبت

با شماره‌ای که مالک صریحاً برای آزمون مجاز کرد، موارد زیر روی Next محلی و وردپرس واقعی موفق شدند:

- ارسال و دریافت OTP واقعی، تأیید کد و اعتبارسنجی هویت با وردپرس.
- صدور کوکی رمزنگاری‌شدهٔ HttpOnly و بررسی نشست در درخواست بعدی.
- افزودن یک کالای موجود به سبد حساب؛ تطبیق اقلام و مبلغ با Store API واقعی ووکامرس.
- حفظ کوکی و نشست در مرورگر واقعی و پس از reload.
- حذف فقط کالای افزوده‌شدهٔ تست و حفظ اقلام اولیهٔ سبد.
- خروج، ابطال نشست و رد درخواست با نسخهٔ قبلی کوکی.

شواهد بدون شماره، کد یا کوکی در `artifacts/auth-cart/live-results.json` ثبت شده‌اند. ابزار قابل اجرای دوباره `npm run test:auth:live` است؛ به تنظیم صریح `AUTH_LIVE_TEST_PHONE` و ورود تعاملی کد نیاز دارد. اگر `AUTH_PLAYWRIGHT_MODULE` تنظیم شود، بررسی مرورگر هم انجام می‌شود. این تست خرید، پرداخت یا تغییر رمز انجام نمی‌دهد.

خروجی build روی یک سرور موقت production محلی نیز اجرا شد: ورود واقعی حساب آزمایشی، اعتبارسنجی درخواست بعدی و صدور کوکی‌های `Secure`، `HttpOnly` و `SameSite=Lax` موفق بودند. این مرحله پیامک دیگری نفرستاد و اقلام سبد را تغییر نداد. نتیجه در `artifacts/auth-cart/production-results.json` است. این بررسی جای آزمون HTTPS و reverse proxy هاست نهایی را نمی‌گیرد.

## تنظیمات هاست production

`npm run build` فقط تنظیمات موردنیاز ساخت را بررسی می‌کند؛ کلید خصوصی نشست و ذخیره‌سازی می‌توانند بعداً روی هاست تأمین شوند. `npm run start` و راه‌اندازی خود Next، تنظیمات کامل اجرای production را بررسی می‌کنند. مبدأ عمومی انتشار باید پیش از build نهایی مشخص باشد چون متغیرهای `NEXT_PUBLIC_` در کد مرورگر تثبیت می‌شوند. محیط اجرای production باید موارد زیر را از قبل داشته باشد:

- `AUTH_SESSION_SECRET` تصادفی، ثابت و محرمانه؛ میان تمام workerهای یک استقرار یکسان.
- `NEXT_PUBLIC_SITE_URL` برابر مبدأ HTTPS فرانت و آدرس‌های صحیح HTTPS وردپرس.
- دیسک پایدار قابل‌نوشتن برای `AUTH_SESSION_DATA_DIR` و `CART_LOCK_DIR`؛ تمام workerها باید ذخیره‌سازی مشترک موردنیاز را ببینند.
- HTTPS، پراکسی با تنظیم درست مبدأ و headerها و استثناکردن مسیرهای ورود، نشست، سبد و تسویه از کش CDN/وردپرس.

برای آزمایش خروجی build روی همان دستگاه، مبدأ `http://localhost:3000` و آدرس‌های loopback `127.0.0.1` و `[::1]` پذیرفته می‌شوند. این استثنا به دامنه‌های عمومی، IP شبکهٔ محلی یا APIهای وردپرس تعمیم پیدا نمی‌کند و ویژگی Secure کوکی‌ها را تغییر نمی‌دهد. مبدأ عمومی انتشار را پیش از build نهایی به دامنهٔ HTTPS واقعی تغییر بده.

```sh
npm run doctor:production
npm run build
npm run start
```

الگوی فعلی با یک پردازش Node و دیسک پایدار سازگار است. محدودکنندهٔ درخواست فعلی در حافظهٔ همان پردازش است. برای چند instance یا serverless، rate limit و ابطال نشست باید store مشترک داشته باشند؛ فایل قفل روی دیسک‌های مستقل هماهنگی ایجاد نمی‌کند. تأیید این زیرساخت به هاست نهایی وابسته است.

## مواردی که برای انتشار کامل باقی‌اند

به‌روزرسانی ۲۰۲۶/۱۰/۲۲: رابط وردپرس ۱٫۱ در `wordpress/nrh-headless-checkout` انتقال مهمان به حساب را با نشست سروری ووکامرس انجام می‌دهد. درخواست حساب با کوکی وردپرس و nonceهای مستقل WP/Store API ارسال می‌شود و Cart-Token برای آن ارسال نمی‌شود. این مسیر بدون تغییر سورس رمزگذاری‌شده Boom و بدون حدس قرارداد sync-cart پیاده و در تست‌های کنترل‌شده بررسی شده است؛ نصب و آزمون روی وردپرس واقعی هنوز لازم است.

گزارش‌های قبلی یک ناسازگاری PHP در آماده‌سازی checkout نشان داده‌اند. این بخش و پرداخت نهایی در آزمون OTP/افزودن کالای این نوبت اجرا نشده‌اند و موفقیتشان ادعا نمی‌شود. برای برچسب «آمادهٔ انتشار کامل»، قرارداد ادغام، سازگاری checkout، پرداخت و زیرساخت واقعی هاست هم باید تکمیل و آزموده شوند.
