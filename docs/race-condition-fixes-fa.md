# رفع race conditionها و بازآزمایی

> یادداشت پاک‌سازی ۲۰۲۶/۱۰/۲۳: گزارش‌ها و تصاویر خام قدیمی با درخواست مالک پروژه حذف شدند. نتایج تاریخی متن این سند حفظ شده‌اند؛ پیوندهای artifacts قدیمی ممکن است موجود نباشند. شواهد فعلی و مرز آزمون زنده در [گزارش امنیت و باگ](security-audit-fa.md) آمده‌اند.


اصلاحات فقط در Next.js، شامل کلاینت و `/api`های خودش انجام شدند. **کد و تنظیمات PHP، وردپرس و ووکامرس تغییر نکردند.** ووکامرس مرجع داده و محاسبات باقی ماند و TanStack Query پاسخ کامل آن را نگه می‌دارد.

[گزارش اولیه](D:/Projects2/nrh_store_nextjs/docs/race-condition-audit-fa.md) و شواهد قبل از اصلاح حفظ شده‌اند. نتیجه‌های تازه در `artifacts/race-conditions/after-fix` هستند.

## قواعدی که در پروژه بعدی هم لازم‌اند

1. `scope` در TanStack فقط همان QueryClient را صف می‌کند؛ هماهنگی چند تب و چند worker را جدا انجام بده.
2. همه عملیات سبد از `cart.api.ts` عبور کنند؛ `fetch` مستقیم در کامپوننت‌ها قفل مرورگر را دور می‌زند.
3. [Web Locks](https://www.w3.org/TR/web-locks/) در HTTPS/localhost و مرورگر دارای این API، تب‌ها را هماهنگ می‌کند. fallback این پروژه فقط صف همان context است؛ bootstrap چندتب به Web Locks وابسته است.
4. فایل قفل هیچ سبد، قیمت یا توکنی ذخیره نمی‌کند؛ نامش هش‌شده است. شناسه داخل [Cart Token ووکامرس](https://developer.woocommerce.com/docs/apis/store-api/cart-tokens) فقط برای نام قفل استفاده می‌شود؛ اعتبار توکن همچنان با Woo است. چرخش انقضا نباید قفل یک سبد را عوض کند.
5. هدر `X-NRH-Cart-Identity` محافظ عملیات قدیمی است و مجوز دسترسی ایجاد نمی‌کند؛ BFF هویت واقعی را از وردپرس می‌گیرد.
6. فقط خطای `cart_session_required`، که پیش از نوشتن برمی‌گردد، اجازه bootstrap و یک POST تازه می‌دهد. پاسخ گم‌شده یا خطای شبکه هرگز باعث تکرار خودکار افزودن نمی‌شود.
7. تأیید آدرس و آماده‌بودن تسویه باید به داده فعلی وابسته باشند؛ یک boolean مستقل کافی نیست.

GET بررسی نشست عمر کوکی auth را تمدید نمی‌کند. nonce منقضی در همان درخواست سروری تمدید می‌شود، بدون اینکه GET کوکی مرورگر را بازنویسی کند.

## نتیجه تست‌ها

- ۲۰ تست auth، ۱۸ تست cart و ۹ تست کاتالوگ: **۴۷ تست قراردادی/امنیتی موفق**.
- ۵ سناریوی سرور و ۳ تست قفل: موفق؛ قفل بین دو پردازش مستقل Node و آزادشدن آن پس از خطا هم بررسی شد.
- ۱۲ سناریوی مرورگر: موفق، با **صفر خطای hydration/runtime**. دو کلیک + در دو تب، POSTهای ۲ و ۳ تولید کردند و هر دو تب به ۳ رسیدند.
- ۱۰ نوبت آزمون زنده: دو افزودن موازی از تعداد ۱ هر بار **۳** ساختند؛ خواندن دوباره پس از ۷۰۰ میلی‌ثانیه هم ۳ بود. سبد مهمان آزمایشی پاک شد.
- خرید در دسکتاپ/موبایل تا فرم تسویه؛ ورود؛ Providerها؛ بنر؛ و ۱۱ مسیر عمومی/محافظت‌شده: موفق تا مرز خطای فعلی بک‌اند تسویه.
- TypeScript و lint موفق؛ دو هشدار قبلی `img` در جست‌وجو باقی‌اند.

## شرایط اجرای cPanel

برنامه به Node.js و `/api`های Next نیاز دارد؛ نام cPanel به‌تنهایی وجود این قابلیت در پلن را مشخص نمی‌کند. `CART_LOCK_DIR` در `.env.example` معرفی شده و پیش‌فرض آن `data/cart-locks` است. همه workerها باید **همان پوشه قابل‌نوشتن با ایجاد انحصاری فایل** را ببینند. چند سرور با دیسک مستقل یا serverless به محل قفل مشترک نیاز دارند. این محافظت مخصوص درخواست‌های عبوری از BFF این پروژه است؛ نوشتن مستقیم سرویس دیگری در Woo خارج از این قفل است.

قفل فعال با زمان منقضی نمی‌شود تا دو نویسنده وارد نشوند. پس از crash پردازش، همه workerها را کامل متوقف کن، فقط فایل‌های `.lock` مانده در پوشه قفل تنظیم‌شده را پاک کن و برنامه را راه بینداز. داده سبد در این فایل‌ها نیست؛ پوشه‌های auth، بنر و وردپرس نباید حذف شوند. خطای دیسک یا انتظار بیش از ۶۰ ثانیه به موفقیت جعلی تبدیل نمی‌شود.

## اجرای دوباره

سرور محلی باید فعال باشد و Playwright در دسترس باشد. وابستگی تازه‌ای نصب نشد.

```powershell
$env:PLAYWRIGHT_MODULE = 'C:\Users\Kiarash\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules\playwright'
$env:RACE_REPORT_DIR = 'artifacts/race-conditions/after-fix'
npm run test:race:server
npm run test:race:locks
npm run test:race:browser
$env:RACE_TRIALS = '10'
npm run test:race:live
```
