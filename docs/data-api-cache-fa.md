# دریافت داده، API داخلی و کش

این پروژه دو مسیر اصلی دریافت داده دارد. مسیر درست را با توجه به محل اجرا انتخاب می‌کنیم:

```text
رندر سروری: صفحه Next → تابع سروری فیچر → Store API ووکامرس
تعامل مرورگر: hook → API داخلی Next → تابع سروری → وردپرس/ووکامرس
```

BFF همان API داخلی متناسب با رابط ماست. وظیفه آن کنترل ورودی، نشست و شکل خطاست. محاسبه قیمت و موجودی سبد همچنان به ووکامرس سپرده می‌شود.

**HTTP در سرور و مرورگر**

[store-client.ts](D:/Projects2/nrh_store_nextjs/lib/woocommerce/store-client.ts) دو تابع دارد: `wcResponse` پاسخ و هدرها را نگه می‌دارد؛ `wcFetch<T>` JSON را برمی‌گرداند. مسیر پایه از `WP_API_URL` ساخته می‌شود، timeout برابر ۱۵ ثانیه است و دنبال‌کردن redirect مجاز نیست. خطا به `WooCommerceApiError` با status/code تبدیل می‌شود.

نوشتن `<T>` اعتبارسنجی runtime ایجاد نمی‌کند. بعضی مصرف‌کننده‌ها آرایه یا شناسه پاسخ را بررسی می‌کنند؛ نباید تصور کرد تمام کاتالوگ با یک schema کامل validate می‌شود.

[کلاینت Axios مرورگر](D:/Projects2/nrh_store_nextjs/lib/http/client.ts) به `/api/catalog` وصل می‌شود و timeout پانزده‌ثانیه‌ای دارد. سبد و ورود، کلاینت HTTP اختصاصی و سیاست خطای خودشان را دارند.

**پراکسی کاتالوگ چگونه محدود شده است؟**

[Route کاتالوگ](D:/Projects2/nrh_store_nextjs/app/api/catalog/[...path]/route.ts) فقط `GET` برای محصولات، محصول عددی، دسته‌ها، دسته عددی، برندها و reviewها را می‌پذیرد. درخواست دلخواه به هر URL یا مسیر خصوصی وردپرس عبور نمی‌کند.

پارامترها allowlist دارند؛ مواردی مثل `search`، `category`، `page` و `per_page` مجازند. مقدار تکراری، ناشناخته یا بیش از ۳۰۰ کاراکتر رد می‌شود. `per_page` تا ۱۰۰ محدود و پیش‌فرض آن ۱۰ است. اعتبارسنجی تمام فیلدها یکسان نیست؛ مثلاً هر رشته allowlistشده لزوماً enum سخت‌گیرانه ندارد. هدرهای `X-WP-Total` و `X-WP-TotalPages` برای صفحه‌بندی منتقل می‌شوند؛ credential مرورگر به ووکامرس پاس داده نمی‌شود.

**چهار کش متفاوت داریم**

| لایه | مثال در پروژه | نکته |
| --- | --- | --- |
| `React.cache()` | `getProductDetails` و DAL | کاهش تکرار در رندر سروری؛ کش دائمی کاربران نیست |
| کش داده Next | `next.revalidate: 300` و tag برابر `catalog` | پیش‌فرض transport کاتالوگ؛ قابل override |
| Query مرورگر | جست‌وجو، زیردسته‌ها، سبد | هر query key و سیاست مستقل دارد |
| HTTP/CDN | کاتالوگ: `s-maxage=60` | تنظیم CDN/میزبان هم روی رفتار واقعی اثر دارد |

[QueryClient](D:/Projects2/nrh_store_nextjs/lib/query-client.ts) پیش‌فرض `staleTime` ده دقیقه، `gcTime` سی دقیقه، یک retry و غیرفعال‌بودن refetch با focus دارد. جست‌وجو و سبد این پیش‌فرض‌ها را تغییر می‌دهند. `staleTime` مدت تازه‌بودن است؛ `gcTime` مدت نگهداری داده بدون observer فعال. `invalidateQueries` داده را قدیمی اعلام می‌کند؛ `setQueryData` پاسخ در دسترس را مستقیماً جایگزین می‌کند.

داده کاتالوگ عمومی قابل کش است. نشست، سبد و checkout پاسخ شخصی `private, no-store` دارند. قاطی‌کردن این دو سیاست می‌تواند سبد یک نشست را به نشست دیگر نشان دهد. مشکل LiteSpeed و دفاع فعلی در [راهنمای سبد](D:/Projects2/nrh_store_nextjs/docs/cart-learning-fa.md) توضیح داده شده است.

**وبهوک و تازه‌سازی کاتالوگ**

ووکامرس می‌تواند `POST /api/catalog/revalidate` را پس از تغییر داده بفرستد. [handler وبهوک](D:/Projects2/nrh_store_nextjs/app/api/catalog/revalidate/route.ts) راز حداقل ۳۲ کاراکتری، سقف بدنه ۲۵۶ KiB و امضای `X-WC-Webhook-Signature` را بررسی می‌کند. امضا HMAC-SHA256 و Base64 روی بایت‌های اصلی بدنه است؛ JSON بازسازی‌شده ممکن است همان امضا را نداشته باشد.

پس از تأیید، `revalidateTag('catalog', 'max')` اجرا می‌شود. طبق [مستندات نسخه نصب‌شده](D:/Projects2/nrh_store_nextjs/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidateTag.md)، `max` از stale-while-revalidate استفاده می‌کند: بازدید بعدی می‌تواند داده قبلی را ببیند و تازه‌سازی در پس‌زمینه انجام شود. وبهوک، تب‌های باز یا کش CDN را خودبه‌خود پاک نمی‌کند. تنظیم رویداد و راز یکسان در پنل ووکامرس همچنان کار استقرار است.

**خطا و محدودسازی**

۴۰۴ محصول با قطعی بک‌اند متفاوت است: اولی به `notFound()` و دومی به مسیر خطا می‌رود. کاتالوگ خطای upstream سروری را به ۵۰۲ امن تبدیل می‌کند. [rate-limit.ts](D:/Projects2/nrh_store_nextjs/lib/server/rate-limit.ts) از Map حافظه استفاده می‌کند؛ با restart پاک می‌شود و میان چند instance مشترک نیست. IP فقط پشت پراکسی قابل اعتماد معنا دارد.

**تمرین:** با Network جست‌وجوی محصول را ببین. `per_page` و پاسخ کاتالوگ را با استفاده سروری همان محصول مقایسه کن. سپس برای یک تغییر محصول، توضیح بده کدام کش‌ها با وبهوک تازه می‌شوند و کدام‌ها نیازمند خواندن مجدد مرورگرند.
